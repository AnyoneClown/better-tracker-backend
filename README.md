# Better Tracker backend

Async FastAPI API for tracking workouts, income and expenses, monthly budgets,
savings, net worth, body weight, and nutrition. This directory contains only the
backend; a frontend can consume the JSON API later.

The API supports multi-user registration and login with email addresses and
passwords. Every tracker endpoint requires a signed bearer token, and every
record, list, aggregate, update, and deletion is scoped to the authenticated
user.

## Architecture

- FastAPI routes and Pydantic request/response schemas under `app/api` and
  `app/schemas`.
- SQLAlchemy 2 async ORM models under `app/models`.
- `asyncpg` through the `sqlalchemy-cockroachdb` dialect, with one async session
  per request.
- Alembic migrations under `alembic`.
- Argon2 password hashes and signed, expiring JWT access tokens. Passwords and
  tokens are never returned by tracker endpoints or stored in plaintext.
- Domain routes for workouts, finance, wealth, and health. UUID primary keys,
  decimal money/measurements, and database constraints preserve data quality.

## Prerequisites

For the recommended setup:

- Docker with Docker Compose v2
- `curl` for the examples

For a fully local setup, use Python 3.13, CockroachDB 26.2, and
[uv](https://docs.astral.sh/uv/).

## Quick start with Docker Compose

Run commands from this project directory:

```bash
cp .env.example .env
docker compose up --build
```

Compose starts CockroachDB, creates the `tracker` database, applies all Alembic
migrations, and starts the API. Once the `migrate` service has completed:

- API: <http://localhost:8000>
- Swagger UI: <http://localhost:8000/docs>
- OpenAPI JSON: <http://localhost:8000/openapi.json>
- CockroachDB SQL: `localhost:26257`
- CockroachDB console: <http://localhost:8080>

The API container has a readiness healthcheck, so scripts can wait for the whole
stack:

```bash
docker compose up -d --build --wait
```

Useful lifecycle commands:

```bash
docker compose logs -f api migrate
docker compose down
```

The named `cockroach-data` volume survives `docker compose down`. Running
`docker compose down -v` also deletes the local database volume and all tracker
data.

### Load local demo data

After the Compose stack is healthy, load the reusable SQL fixture:

```bash
docker compose exec -T db /cockroach/cockroach sql \
  --insecure --host=localhost:26257 --database=tracker \
  < scripts/seed_dev.sql
```

The fixture populates July 2026 with representative finance, workout, body,
nutrition, savings, and net-worth records. It uses stable UUIDs, so rerunning it
updates the fixture rows instead of duplicating them, and it does not delete
other local records. Log in with `demo@example.com` / `DemoPassword1!` to view
the seeded records; these credentials are for local development only.

## Database migrations

Compose runs `alembic upgrade head` before starting the API. To apply migrations
again to the Compose database:

```bash
docker compose run --rm migrate alembic upgrade head
```

Create and inspect revisions from a local development environment so the new
file is written into this checkout:

```bash
uv run alembic revision --autogenerate -m "describe the schema change"
uv run alembic upgrade head
uv run alembic current
uv run alembic history
uv run alembic check
```

Review every autogenerated revision before applying it. To reverse one revision
locally, use `uv run alembic downgrade -1` only after checking that its downgrade
is safe for the stored data.

The ownership migration preserves rows created by the former single-user API by
leaving their `user_id` empty. Those legacy rows are intentionally invisible to
API users until an administrator assigns them to a registered user's UUID.

## Local setup without Docker

Start a local insecure CockroachDB node and create the database:

```bash
cockroach start-single-node \
  --insecure \
  --listen-addr=localhost:26257 \
  --http-addr=localhost:8080 \
  --store=./.cockroach-data \
  --background
cockroach sql --insecure --host=localhost:26257 \
  --execute='CREATE DATABASE IF NOT EXISTS tracker;'
```

Install the application and development dependencies, migrate, and run it:

```bash
cp .env.example .env
uv sync --extra dev
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

The default `DATABASE_URL` in `.env.example` targets this local node. Stop it
with `cockroach quit --insecure --host=localhost:26257` when finished.

## Configuration

Settings are read from environment variables and, for local commands, `.env`.

| Variable | Default | Purpose |
| --- | --- | --- |
| `APP_NAME` | `Better Tracker API` | OpenAPI application title. |
| `ENVIRONMENT` | `development` | Deployment environment label. |
| `DATABASE_URL` | `cockroachdb+asyncpg://root@localhost:26257/tracker` | Database URL used by a host-run API and Alembic. |
| `COMPOSE_DATABASE_URL` | `cockroachdb+asyncpg://root@db:26257/tracker` | URL that Compose maps to `DATABASE_URL` inside app containers. |
| `DATABASE_ECHO` | `false` | Set to `true` to log generated SQL. |
| `CORS_ORIGINS` | `["http://localhost:3000"]` | JSON array of allowed frontend origins. |
| `JWT_SECRET_KEY` | Development-only value | Secret used to sign access tokens. Set a random value of at least 32 characters; the development default is rejected outside development/test. |
| `JWT_ISSUER` | `better-tracker-api` | Required JWT issuer claim. |
| `JWT_AUDIENCE` | `better-tracker-api` | Required JWT audience claim. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | Access-token lifetime, from 1 minute to 24 hours. |

## API overview

Resource endpoints use `/api/v1`; generated Swagger documentation contains the
complete request and response schemas.

### Authentication

- `POST /api/v1/auth/register` — create a user with a unique, normalized email
  address and an Argon2-hashed password. Passwords must be 8–128 characters and
  include lowercase, uppercase, numeric, and special characters. Duplicate
  email addresses return `409 Conflict`.
- `POST /api/v1/auth/login` — exchange an email address and password for a
  signed access token. Invalid email/password combinations return the same
  generic `401 Unauthorized` response.
- `GET /api/v1/auth/me` — return the active user represented by a bearer token.

All workout, finance, wealth, and health routes require
`Authorization: Bearer <access_token>`. Requests can only access records owned
by that token's user; another user's resource identifier returns `404 Not Found`.

### System

- `GET /` — service links.
- `GET /healthz` — process liveness.
- `GET /readyz` — readiness, including a database query.
- `GET /docs`, `GET /redoc`, `GET /openapi.json` — generated API documentation.

### Workouts

- `POST /api/v1/workouts` — create a workout and nested sets.
- `GET /api/v1/workouts/summary` — aggregate workouts, active minutes, sets,
  reps, weight volume, distance, and timed-set duration, including an
  exercise breakdown. Optional `date_from` and `date_to` filters must include
  timezone offsets.
- `GET /api/v1/workouts` — list with `date_from`, `date_to`, `offset`, and
  `limit` filters. Date-time filters must include a timezone offset.
- `GET|PATCH|DELETE /api/v1/workouts/{workout_id}` — read, update, or delete a
  workout. If `sets` is present in a PATCH, it replaces all existing sets;
  omit it to retain them or send `[]` to clear them. Every set needs at least
  one of reps, weight, distance, or duration.

### Cash flow and budgets

- `GET /api/v1/finance/summary?year=YYYY&month=M&currency=USD` — monthly income,
  expense, budget, and per-category totals.
- `POST|GET /api/v1/finance/transactions` — create or list transactions. List
  filters: `kind` (`income` or `expense`), `category`, `currency`, `start_date`,
  `end_date`, `offset`, and `limit`.
- `GET|PATCH|DELETE /api/v1/finance/transactions/{transaction_id}` — transaction
  detail and mutations.
- `POST|GET /api/v1/finance/budgets` — create or list category budgets. List
  filters: `year`, `month`, `category`, `currency`, `offset`, and `limit`.
- `GET|PATCH|DELETE /api/v1/finance/budgets/{budget_id}` — budget detail and
  mutations.

Categories are stored as normalized lowercase values with repeated whitespace
collapsed. This keeps transaction filters and category budgets aligned when a
caller sends variants such as `Food`, `food`, or ` food `.

### Wealth, savings, and net worth

- `GET /api/v1/wealth/summary?currency=USD` — assets, liabilities, net worth,
  savings, and savings-goal totals.
- `POST|GET /api/v1/wealth/accounts` — create or list accounts; filter by
  `account_type` (`asset` or `liability`), `currency`, `offset`, and `limit`.
- `GET|PATCH|DELETE /api/v1/wealth/accounts/{account_id}` — account detail and
  mutations.
- `POST|GET /api/v1/wealth/savings-goals` — create or list goals; filter by
  `currency`, `offset`, and `limit`.
- `GET|PATCH|DELETE /api/v1/wealth/savings-goals/{goal_id}` — goal detail and
  metadata mutations. `current_amount` can be set when a goal is created and
  is then changed through contribution history, rather than overwritten by a
  generic PATCH.
- `POST|GET /api/v1/wealth/savings-goals/{goal_id}/contributions` — record or
  list dated contributions and withdrawals. Mutations update the goal balance
  in the same database transaction and reject withdrawals that would make it
  negative.
- `GET|PATCH|DELETE /api/v1/wealth/savings-contributions/{contribution_id}` —
  contribution detail and mutations; edits and deletion adjust the goal
  balance atomically.
- `POST /api/v1/wealth/net-worth-snapshots/capture` — capture current account
  totals with a server-generated current timestamp. Backdated timestamps are
  deliberately rejected because the API does not retain historical account
  balances from which to reconstruct them.
- `GET /api/v1/wealth/net-worth-snapshots` — list snapshots with `currency`,
  `offset`, and `limit` filters.
- `GET /api/v1/wealth/net-worth-snapshots/{snapshot_id}` — snapshot detail.
- `DELETE /api/v1/wealth/net-worth-snapshots/{snapshot_id}` — delete a snapshot.

### Weight and nutrition

- `POST|GET /api/v1/health/weights` — create or list weight entries; filter by
  `start_date`, `end_date`, `offset`, and `limit`.
- `GET|PATCH|DELETE /api/v1/health/weights/{entry_id}` — weight detail and
  mutations.
- `POST|GET /api/v1/health/nutrition` — create or list daily calorie/macro logs;
  filter by `start_date`, `end_date`, `offset`, and `limit`.
- `GET|PATCH|DELETE /api/v1/health/nutrition/{log_id}` — nutrition detail and
  mutations.
- `GET /api/v1/health/summary` — weight change and nutrition aggregates, with
  optional `start_date` and `end_date`.

Collection limits are capped at 100. PATCH requests change only supplied fields,
apart from the documented workout-set replacement behavior.

Every collection response uses an `{items, total, offset, limit}` envelope so a
frontend can paginate without a second counting request.

## Example curl workflow

```bash
BASE_URL=http://localhost:8000

curl -fsS "$BASE_URL/readyz"

curl -fsS -X POST "$BASE_URL/api/v1/auth/register" \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "user@example.com",
    "password": "StrongPassword1!"
  }'

curl -fsS -X POST "$BASE_URL/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "user@example.com",
    "password": "StrongPassword1!"
  }'

# Copy access_token from the login response.
TOKEN='<access_token>'
AUTH_HEADER="Authorization: Bearer $TOKEN"

curl -fsS -X POST "$BASE_URL/api/v1/workouts" \
  -H "$AUTH_HEADER" \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Full body",
    "performed_at": "2026-07-24T18:00:00+03:00",
    "duration_minutes": 55,
    "sets": [
      {"exercise": "Squat", "set_number": 1, "reps": 8, "weight_kg": "80"},
      {"exercise": "Squat", "set_number": 2, "reps": 8, "weight_kg": "80"},
      {"exercise": "Run", "set_number": 1, "distance_km": "3.5"}
    ]
  }'

curl -fsS -H "$AUTH_HEADER" "$BASE_URL/api/v1/workouts?offset=0&limit=20"

curl -fsS -X POST "$BASE_URL/api/v1/finance/transactions" \
  -H "$AUTH_HEADER" \
  -H 'Content-Type: application/json' \
  -d '{
    "kind": "expense",
    "amount": "50.00",
    "category": "fitness",
    "occurred_on": "2026-07-24",
    "currency": "USD",
    "description": "Monthly gym fee"
  }'

curl -fsS -X POST "$BASE_URL/api/v1/finance/budgets" \
  -H "$AUTH_HEADER" \
  -H 'Content-Type: application/json' \
  -d '{
    "year": 2026,
    "month": 7,
    "category": "fitness",
    "currency": "USD",
    "limit_amount": "200.00"
  }'

curl -fsS -H "$AUTH_HEADER" \
  "$BASE_URL/api/v1/finance/summary?year=2026&month=7&currency=USD"
```

Create responses contain UUIDs used by the corresponding detail, PATCH, and
DELETE endpoints.

## Tests and quality checks

After `uv sync --extra dev`:

```bash
uv run pytest
uv run ruff format --check .
uv run ruff check .
uv run mypy app
```

GitHub Actions runs Ruff linting/format validation and the default pytest suite
on pushes to `main`, pull requests, and manual workflow dispatches. The fast
default API tests use a disposable async SQLite database; the guarded
integration suite below remains the source of truth for CockroachDB migrations,
constraints, and dialect behavior.

The default suite skips the destructive integration smoke test. With the
Compose database running, execute it against its guarded, disposable
`tracker_test` database:

```bash
docker compose up -d db
RUN_COCKROACH_INTEGRATION=1 \
DATABASE_URL=cockroachdb+asyncpg://root@localhost:26257/tracker_test \
uv run pytest -m integration
```

The fixture refuses database names outside `tracker_test`/`tracker_test_*`,
recreates that database, applies the migration from blank, exercises all
tracker domains, and drops it afterward.

## CockroachDB safety and production notes

The Compose and local commands use a single-node CockroachDB process with
`--insecure`. It has no transport encryption or database authentication; port
26257 and the admin console must remain local. This mode is for development
only.

For production, use a secure CockroachDB deployment or CockroachDB Cloud, a
least-privileged SQL user, certificate-verified TLS, secret-managed connection
credentials, a strong secret-managed `JWT_SECRET_KEY`, HTTPS, and restricted
CORS origins. Replace the local URL with the secure
`cockroachdb+asyncpg://` connection details for that cluster.

The SQLAlchemy engine uses CockroachDB's `SERIALIZABLE` isolation. Under write
contention, CockroachDB can return SQLSTATE `40001` and require the complete
transaction to be retried. The current API does not provide a general retry
wrapper. Before production, add bounded retries with jitter around idempotent
units of work, using a fresh async session for each attempt and keeping external
side effects outside the retried callback. Do not blindly retry ambiguous commit
errors (`40003`) without an idempotency strategy.

Financial transactions, account balances, and savings goals are intentionally
separate ledgers in this MVP. Recording income or an expense does not silently
change an account balance; update the relevant account explicitly. Nutrition is
stored as one aggregate per day rather than individual meals, and summaries are
always calculated within one requested currency because no exchange-rate source
is configured.
